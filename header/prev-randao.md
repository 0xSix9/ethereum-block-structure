# Ethereum Block Header Explained: What Is prevRandao?

When people first study the Ethereum block header, fields such as `timestamp`, `gasLimit`, `gasUsed`, and `baseFeePerGas` are relatively easy to understand.

But one field is particularly interesting because it connects the **Execution Layer** with Ethereum's Proof of Stake consensus mechanism:

**`prevRandao`**

The `prevRandao` field is a value derived from the randomness mechanism of Ethereum's Beacon Chain and is made available to the Execution Layer. It can also be accessed by smart contracts through the `block.prevrandao` variable.

Understanding this field requires understanding Ethereum's transition from Proof of Work to Proof of Stake.

## What Is prevRandao?

`prevRandao` is a field in Ethereum's execution payload/header that contains a value derived from the Beacon Chain's RANDAO randomness mechanism.

Ethereum uses this value as a source of protocol randomness, including for validator selection.

The Ethereum execution-layer block structure includes `prev_randao` as one of its fields.

In Solidity, this value is exposed through:

`block.prevrandao`

Solidity's documentation describes `block.prevrandao` as the random number provided by the Beacon Chain for EVM versions from Paris onward.

However, calling it simply "a random number" can be misleading.

It is better to think of `prevRandao` as **a protocol-generated randomness value with specific security properties**, rather than as a perfectly unpredictable random number.

## Why Does Ethereum Need Randomness?

Randomness is extremely useful in a Proof of Stake blockchain.

Ethereum needs randomness for several protocol-level operations, especially determining which validators participate in different roles.

For example, randomness is involved in selecting validators for proposer and committee duties.

Without a source of randomness, an attacker could potentially predict or manipulate validator assignments much more easily.

Ethereum's Beacon Chain therefore maintains a continuously evolving source of randomness through its RANDAO mechanism.

The resulting randomness is made available to the Execution Layer through `prevRandao`.

## What Is RANDAO?

RANDAO is Ethereum's mechanism for accumulating randomness from validator contributions.

Validators participate in the Beacon Chain's consensus process and contribute information that is combined into the evolving randomness state.

The important idea is that Ethereum does not rely on one validator generating a random number by itself.

Instead, randomness is accumulated across the validator set over time.

The resulting value can then be used by the protocol and exposed to the Execution Layer.

## Why Is It Called prevRandao?

The name `prevRandao` comes from the fact that the value available in an execution block is derived from the randomness state associated with the **previous Beacon Chain state**.

EIP-4399 specifies that, after the Proof of Stake transition, the `mixHash` field in the execution block header is used to carry the latest RANDAO mix from the previous Beacon Chain state. The field was subsequently referred to as `prevRandao`.

The name therefore reflects its relationship with the previous RANDAO value rather than indicating that it is simply a random number generated by the current block producer.

## What Happened to the Old Difficulty Field?

To understand `prevRandao`, we need to look at Ethereum before The Merge.

During the Proof of Work era, Ethereum blocks contained a `difficulty` field.

This field represented the mining difficulty and was an important part of the Proof of Work system.

Smart contracts could access this value through the EVM's `DIFFICULTY` opcode.

After Ethereum transitioned to Proof of Stake, mining difficulty was no longer meaningful.

Ethereum therefore needed to change what this existing EVM mechanism represented.

This was the purpose of **EIP-4399**.

EIP-4399 changed the semantics of the `DIFFICULTY` opcode so that it would return the Beacon Chain's RANDAO output instead of Proof of Work difficulty. The opcode was renamed to `PREVRANDAO`, while retaining opcode number `0x44`.

## The Relationship Between mixHash and prevRandao

Before The Merge, the `mixHash` field was associated with Proof of Work.

After The Merge, Ethereum reused this existing 32-byte field instead of adding a completely new field to the block header.

The field was repurposed to contain the RANDAO value.

EIP-4399 explicitly chose this approach because reusing the existing field avoided increasing the block header size by another 32 bytes.

This is an interesting example of how Ethereum evolved its existing data structures instead of unnecessarily expanding them.

## prevRandao and the Execution Layer

One of the important design decisions behind `prevRandao` is that the Execution Layer can access the randomness value directly through the execution payload.

The execution payload is passed from the Consensus Layer to the Execution Layer as part of Ethereum's Proof of Stake block structure.

This allows the EVM to execute transactions using a block-specific randomness value without requiring the Execution Layer to independently reconstruct the entire Beacon Chain randomness process.

Conceptually, the flow looks like this:

Beacon Chain
↓
RANDAO randomness
↓
`prevRandao`
↓
Execution Payload
↓
EVM
↓
`block.prevrandao`

This is one of the clearest examples of information moving between Ethereum's Consensus Layer and Execution Layer.

## How Can a Smart Contract Access prevRandao?

Smart contracts can access the value through Solidity's global block variable:

```solidity
block.prevrandao
```

For example:

```solidity
contract RandomnessExample {
    function getRandomness() external view returns (uint256) {
        return block.prevrandao;
    }
}
```

The returned value is a `uint256`.

Under the hood, the EVM obtains this information through the `PREVRANDAO` opcode, which uses opcode `0x44`.

## Is prevRandao Truly Random?

This is one of the most important questions.

**No, `prevRandao` should not be treated as a perfectly random and completely manipulation-resistant source of randomness.**

Ethereum's own EIP-4399 specification discusses both the **biasability** and **predictability** of this randomness source.

A block proposer has some influence over the randomness because the proposer can choose not to publish a block.

This means a malicious proposer may have limited ability to influence the randomness available in a particular situation.

However, that influence is constrained.

The randomness is continuously updated by validator participation, and an honest future contribution can reduce the effect of a previous proposer attempting to bias the value.

## Why Can't a Validator Completely Control prevRandao?

A common misconception is that the validator proposing a block simply chooses any random number it wants.

That is not how the system works.

The proposer does not have unrestricted control over the Beacon Chain's RANDAO state.

Instead, the proposer has limited influence over whether its contribution is revealed and whether a block is published.

EIP-4399 describes this as approximately **one bit of influence per slot** for the proposer.

This distinction is extremely important.

`prevRandao` is therefore better described as a **biasable but useful source of on-chain randomness** rather than a cryptographically perfect random oracle.

## prevRandao vs blockhash

Before Proof of Stake, developers sometimes used `blockhash` as a source of pseudo-randomness.

After The Merge, `prevRandao` provides a different and generally stronger source of randomness for many applications.

The Ethereum Foundation specifically notes that post-Merge `PREVRANDAO` provides stronger randomness properties than `BLOCKHASH`, although it remains biasable.

This does not mean that developers should blindly use `block.prevrandao` for every application.

For applications involving significant financial value, stronger randomness mechanisms may still be appropriate.

## What Can prevRandao Be Used For?

`prevRandao` can be useful when a smart contract needs a source of unpredictable on-chain entropy.

Potential applications include:

* Randomized selection
* NFT trait assignment
* Validator-related applications
* Games with low-value randomness requirements
* Randomized protocol operations
* Applications that need a source of blockchain-native entropy

However, the security requirements of the application are extremely important.

A simple game with negligible financial value may tolerate the properties of `prevRandao`.

A high-value lottery or gambling protocol should not assume that `prevRandao` is impossible to influence.

## Why Lookahead Matters

One of the most important concepts when using `prevRandao` is **lookahead**.

If an application uses randomness that is going to be generated far enough in the future, it becomes harder for an attacker to manipulate the outcome based on their knowledge of current validator assignments.

EIP-4399 recommends using a reasonably high lookahead when applications depend on future randomness. It discusses multiple-epoch lookahead as a way to reduce predictability and the ability of participants to influence the outcome.

The basic idea is simple:

The farther into the future the randomness is used, the harder it becomes for an attacker to know exactly how the relevant randomness will evolve.

## prevRandao Is Not Part of Ethereum State

Another important distinction is that `prevRandao` is not a value stored in a smart contract's storage.

It is part of the block execution environment.

Just like `block.timestamp` and `block.number`, it provides contextual information about the block in which a transaction is being executed.

The EVM exposes these block-related values as part of the execution environment.

This means that a smart contract can read `block.prevrandao`, but it does not store that value automatically in its own state.

## Why Is prevRandao Important for Developers?

For a typical Solidity developer, `prevRandao` may initially look like just another block variable.

But it represents something much deeper.

It connects:

**Beacon Chain → Proof of Stake → RANDAO → Execution Payload → EVM → Smart Contracts**

Understanding this chain of relationships helps developers understand how Ethereum's two major layers interact.

It also becomes important when building:

* Smart contracts requiring randomness
* Blockchain infrastructure
* Ethereum clients
* Indexers
* Block explorers
* Protocol-level applications
* MEV-related systems

## A Historical Perspective

The evolution of this field is particularly interesting.

During Proof of Work:

`difficulty`
↓
Mining difficulty
↓
`DIFFICULTY` opcode

After The Merge:

`prevRandao`
↓
Beacon Chain randomness
↓
`PREVRANDAO` opcode

Ethereum did not simply introduce an entirely new mechanism.

Instead, EIP-4399 repurposed existing infrastructure to expose a new source of randomness while preserving compatibility with the existing EVM opcode position.

## Final Thoughts

`prevRandao` is much more than another field in the Ethereum block header.

It represents the connection between Ethereum's Proof of Stake consensus mechanism and the EVM.

Its value originates from the Beacon Chain's RANDAO mechanism and is included in the execution payload so that the EVM and smart contracts can access it.

For Solidity developers, it is available through:

```solidity
block.prevrandao
```

For protocol developers, it provides an important example of how the Consensus Layer supplies information to the Execution Layer.

And for anyone building applications that require randomness, it is essential to understand both its strengths and its limitations.

The most important lesson is simple:

**`prevRandao` provides useful on-chain randomness, but it is not a perfect source of randomness.**

Understanding that distinction is essential for building secure Ethereum applications.
