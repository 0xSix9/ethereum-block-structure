# What Is the `receiptsRoot` in an Ethereum Block Header?

When studying the Ethereum block structure, you will encounter several important **root hashes** inside the block header.

Three of the most important are:

* `stateRoot`
* `transactionsRoot`
* `receiptsRoot`

Although all three are root hashes, they represent **completely different types of data**.

The `transactionsRoot` commits to the transactions included in the block.

The `stateRoot` commits to Ethereum's global state after the block has been executed.

The `receiptsRoot` commits to the **transaction receipts generated by executing the transactions in the block**.

Understanding `receiptsRoot` is therefore essential for understanding how Ethereum cryptographically commits to the **results and execution information of transactions**.

---

## 1. What Is `receiptsRoot`?

`receiptsRoot` is a field in the Ethereum block header that contains the **root hash of the receipt trie** for that block.

In simplified form:

```text
Block
│
├── Block Header
│   │
│   ├── parentHash
│   ├── stateRoot
│   ├── transactionsRoot
│   ├── receiptsRoot
│   └── ...
│
├── Transactions
│
└── Other Block Data
```

The `receiptsRoot` is a cryptographic commitment to the collection of **transaction receipts produced by the transactions in that block**.

It allows Ethereum to commit to the receipts without storing every receipt directly inside the block header.

The header only needs to store a single 32-byte root hash.

---

# 2. What Is a Transaction Receipt?

Before understanding `receiptsRoot`, we need to understand what a **transaction receipt** is.

A transaction is a request submitted to Ethereum.

For example, a transaction might:

* transfer ETH,
* call a smart contract,
* create a contract,
* interact with a token,
* emit events.

After the transaction is executed, Ethereum produces a receipt containing information about the execution.

A receipt can contain information such as:

* transaction status
* gas used
* logs generated during execution
* log bloom

For example, conceptually:

```text
Transaction
     │
     ▼
Execution
     │
     ▼
Transaction Receipt
     │
     ├── Status
     ├── Gas Used
     ├── Logs
     └── Logs Bloom
```

So the receipt is essentially a record of important **execution results and logs** associated with a transaction.

---

# 3. Transaction vs Transaction Receipt

It is very important not to confuse a transaction with its receipt.

A transaction describes **what the sender asked Ethereum to do**.

A receipt describes important information about **what happened when Ethereum executed that transaction**.

For example:

```text
Transaction
────────────────────
From: Alice
To: Bob
Value: 1 ETH
Signature: ...
Nonce: ...
```

After execution:

```text
Receipt
────────────────────
Status: Successful
Gas Used: ...
Logs: ...
Bloom: ...
```

Therefore:

```text
Transaction ≠ Receipt
```

And consequently:

```text
transactionsRoot ≠ receiptsRoot
```

They commit to different datasets.

---

# 4. Where Is `receiptsRoot` Stored?

`receiptsRoot` is stored inside the **Ethereum block header**.

A simplified Ethereum block can be represented as:

```text
Block
│
├── Header
│   │
│   ├── parentHash
│   ├── stateRoot
│   ├── transactionsRoot
│   ├── receiptsRoot
│   ├── logsBloom
│   ├── blockNumber
│   ├── gasLimit
│   ├── gasUsed
│   ├── timestamp
│   └── ...
│
├── Transactions
│
└── Withdrawals / Other Data
```

The important point is that the actual collection of receipts is **not placed directly inside the header**.

Instead, Ethereum constructs a trie from the receipts and stores the resulting root hash in the header.

---

# 5. The Receipt Trie

Ethereum uses a **Modified Merkle Patricia Trie (MPT)** structure for its receipt commitment.

Conceptually:

```text
                 receiptsRoot
                      │
                      ▼
                ┌───────────┐
                │   Root    │
                └─────┬─────┘
                      │
             ┌────────┴────────┐
             ▼                 ▼
          Branch              Branch
          /    \              /    \
         ▼      ▼            ▼      ▼
      Receipt  Receipt     Receipt  Receipt
```

The trie organizes receipts according to their transaction index.

For example:

```text
Transaction Index
       │
       ▼
      0
      1
      2
      3
      4
      ...
```

The receipts are inserted into the receipt trie using their transaction indexes as keys.

After constructing the trie, Ethereum calculates its root hash.

That root hash becomes:

```text
receiptsRoot
```

---

# 6. Why Does Ethereum Need a Root Hash?

Imagine a block contains 200 transactions.

Each transaction can produce a receipt.

Therefore, there may be hundreds of receipts associated with the block.

It would be inefficient to put all of those receipts inside the block header.

Instead, Ethereum compresses the commitment to the entire receipt dataset into a single hash.

Conceptually:

```text
Receipts
─────────────────────────────
Receipt 0
Receipt 1
Receipt 2
Receipt 3
...
Receipt 199
        │
        ▼
Receipt Trie
        │
        ▼
     Hashing
        │
        ▼
receiptsRoot
```

The result is a single 32-byte value.

This is extremely useful because changing even one receipt would change the resulting root hash.

---

# 7. The Relationship Between Receipts and `receiptsRoot`

Suppose a block contains three transactions:

```text
Transaction 0
Transaction 1
Transaction 2
```

After execution, Ethereum produces:

```text
Receipt 0
Receipt 1
Receipt 2
```

These receipts are inserted into the receipt trie:

```text
Receipt 0 ──┐
Receipt 1 ──┼──> Receipt Trie ──> receiptsRoot
Receipt 2 ──┘
```

The resulting root is stored in the block header:

```text
Block Header
│
└── receiptsRoot
```

Therefore, the relationship can be summarized as:

```text
Transactions
     │
     ▼
Execution
     │
     ▼
Receipts
     │
     ▼
Receipt Trie
     │
     ▼
receiptsRoot
     │
     ▼
Block Header
```

---

# 8. What Information Does a Receipt Contain?

Ethereum transaction receipts contain important information about transaction execution.

At a conceptual level, a receipt includes:

### Status

The status indicates whether execution was successful or reverted.

For example:

```text
1 = successful
0 = reverted
```

### Cumulative Gas Used

This represents the cumulative amount of gas used by transactions up to that point in the block.

### Logs

Smart contracts can emit logs during execution.

For example, an ERC-20 token transfer can emit a `Transfer` event.

Conceptually:

```text
Contract Execution
       │
       ▼
   Emit Event
       │
       ▼
      Log
       │
       ▼
   Transaction Receipt
```

### Logs Bloom

The receipt also contains a bloom filter derived from the logs.

It allows clients to efficiently filter for potentially relevant logs without examining every log individually.

---

# 9. `receiptsRoot` and Smart Contract Events

One of the most important practical uses of receipts is their relationship with **event logs**.

Suppose a user transfers an ERC-20 token.

The smart contract may emit:

```text
Transfer(
    from,
    to,
    amount
)
```

The event becomes part of the transaction's logs.

The logs are included in the receipt.

The receipt is committed into the receipt trie.

The receipt trie contributes to:

```text
receiptsRoot
```

So conceptually:

```text
Smart Contract
      │
      ▼
Event / Log
      │
      ▼
Transaction Receipt
      │
      ▼
Receipt Trie
      │
      ▼
receiptsRoot
```

This creates a cryptographic commitment to the receipts and their associated logs.

---

# 10. `receiptsRoot` vs `transactionsRoot`

These two fields are often confused because both are related to transactions.

But they commit to different things.

## `transactionsRoot`

Commits to the **transactions included in the block**.

```text
Transactions
     │
     ▼
Transaction Trie
     │
     ▼
transactionsRoot
```

## `receiptsRoot`

Commits to the **receipts generated by executing those transactions**.

```text
Transactions
     │
     ▼
Execution
     │
     ▼
Receipts
     │
     ▼
Receipt Trie
     │
     ▼
receiptsRoot
```

The fundamental difference is:

```text
transactionsRoot
      ↓
"What transactions are included?"

receiptsRoot
      ↓
"What execution receipts were produced?"
```

---

# 11. `receiptsRoot` vs `stateRoot`

The distinction becomes even more important when comparing `receiptsRoot` with `stateRoot`.

### `stateRoot`

The `stateRoot` commits to Ethereum's **global state after the block has been executed**.

The state includes information associated with accounts, such as:

* account balances
* nonces
* contract code references
* contract storage

Conceptually:

```text
Previous State
      │
      ▼
Execute Transactions
      │
      ▼
New Global State
      │
      ▼
State Trie
      │
      ▼
stateRoot
```

### `receiptsRoot`

The `receiptsRoot` commits to the **transaction receipts produced during execution**.

```text
Transactions
      │
      ▼
Execute Transactions
      │
      ├───────────────┐
      ▼               ▼
New State         Receipts
      │               │
      ▼               ▼
State Trie       Receipt Trie
      │               │
      ▼               ▼
stateRoot        receiptsRoot
```

This is one of the most important relationships to understand.

---

# 12. The Three Important Root Hashes

We can now summarize the three fields:

| Root               | Commits To            | Main Question                                |
| ------------------ | --------------------- | -------------------------------------------- |
| `transactionsRoot` | Transactions          | What transactions are in this block?         |
| `receiptsRoot`     | Transaction receipts  | What receipts were produced?                 |
| `stateRoot`        | Global Ethereum state | What is the resulting state after execution? |

A useful mental model is:

```text
              Block
                │
       ┌────────┼────────┐
       │        │        │
       ▼        ▼        ▼
 Transactions Receipts  State
       │        │        │
       ▼        ▼        ▼
    Trie      Trie      Trie
       │        │        │
       ▼        ▼        ▼
transactions receipts   state
    Root       Root      Root
```

---

# 13. Does `receiptsRoot` Store the Receipts?

No.

This is an important distinction.

The `receiptsRoot` itself is **only a root hash**.

It does not contain all receipt information.

Instead:

```text
Receipts
   │
   ▼
Receipt Trie
   │
   ▼
Root Hash
   │
   ▼
receiptsRoot
```

The root hash acts as a cryptographic commitment to the receipt trie.

The actual receipt data can be retrieved through Ethereum clients and APIs.

---

# 14. What Happens If a Receipt Changes?

Suppose a block has:

```text
Receipt 0
Receipt 1
Receipt 2
```

and the resulting root is:

```text
receiptsRoot = ABC...
```

Now imagine Receipt 1 changes.

Even a small change to the receipt data changes its hash contribution.

That change propagates upward through the trie.

Eventually, the root changes:

```text
Receipt 1
   │
   ▼
Trie Node
   │
   ▼
Parent Node
   │
   ▼
Root
```

Therefore:

```text
Receipt changes
      ↓
Trie changes
      ↓
Root changes
      ↓
receiptsRoot changes
```

This property provides strong tamper detection.

---

# 15. Why Is This Cryptographically Important?

The block header is itself cryptographically committed to by the block hash.

Therefore, when `receiptsRoot` is included in the block header, the block header effectively commits to the receipt trie.

The chain becomes conceptually linked like this:

```text
Receipts
   │
   ▼
Receipt Trie
   │
   ▼
receiptsRoot
   │
   ▼
Block Header
   │
   ▼
Block Hash
   │
   ▼
Blockchain
```

If someone tried to alter a receipt, they would need to change the receipt trie and therefore the `receiptsRoot`.

But changing `receiptsRoot` changes the block header and therefore the block hash.

This is why the root hash provides a strong cryptographic commitment.

---

# 16. Can We Prove That a Receipt Belongs to a Block?

Yes.

This is one of the important properties of Merkle-based structures.

A client can potentially receive:

```text
Receipt
+
Proof
+
receiptsRoot
```

and verify that the receipt corresponds to a particular position in the receipt trie.

Conceptually:

```text
Receipt
   │
   ▼
Proof
   │
   ├── Node Hash
   ├── Node Hash
   ├── Node Hash
   └── ...
   │
   ▼
Calculated Root
   │
   ▼
Compare With
   │
   ▼
Block Header's receiptsRoot
```

If:

```text
Calculated Root == receiptsRoot
```

the proof is consistent with the committed receipt trie.

This is the fundamental idea behind a **Merkle proof**.

---

# 17. Why Is This Useful for Light Clients?

A light client does not necessarily need to maintain the entire Ethereum dataset.

Instead, it can use cryptographic commitments and proofs.

For example:

```text
Block Header
     │
     └── receiptsRoot
             │
             ▼
        Receipt Proof
             │
             ▼
        Transaction Receipt
```

The client can verify the relationship without needing to independently reconstruct the entire receipt dataset.

This is one of the major advantages of cryptographic commitment structures.

# 18. Example: A Successful ETH Transfer

Imagine Alice sends 1 ETH to Bob.

The transaction is:

```text
Alice
  │
  │  Send 1 ETH
  ▼
Bob
```

Ethereum executes the transaction.

The execution produces a receipt:

```text
Receipt
──────────────
Status: Success
Gas Used: ...
Logs: ...
```

The receipt is inserted into the receipt trie.

The trie produces:

```text
receiptsRoot
```

The value is then stored in the block header:

```text
Block Header
│
├── transactionsRoot
├── receiptsRoot
├── stateRoot
└── ...
```

At the same time, executing the transaction changes Ethereum's global state.

Therefore:

```text
Transaction
     │
     ├───────────────┐
     ▼               ▼
 Receipt          State Changes
     │               │
     ▼               ▼
Receipt Trie      State Trie
     │               │
     ▼               ▼
receiptsRoot      stateRoot
```

This demonstrates why the two root hashes are different even though they are produced from the execution of the same transaction.

# 19. A Smart Contract Example

Consider a token transfer:

```text
Alice
   │
   │ transfer 100 USDC
   ▼
Token Contract
```

The smart contract executes and emits an event:

```text
Transfer(
    Alice,
    Bob,
    100
)
```

The event becomes a log.

The log becomes part of the transaction receipt.

The receipt is committed into the receipt trie.

The resulting root becomes:

```text
receiptsRoot
```

Meanwhile, the token balances in the contract's storage change.

Those state changes ultimately contribute to:

```text
stateRoot
```

So:

```text
Token Transfer
      │
      ├───────────────┐
      ▼               ▼
     Logs          State Changes
      │               │
      ▼               ▼
   Receipt         New State
      │               │
      ▼               ▼
Receipt Trie       State Trie
      │               │
      ▼               ▼
receiptsRoot       stateRoot
```

This is a very useful way to understand the relationship between execution results and Ethereum's state.

# 20. Is `receiptsRoot` the Hash of All Receipts?

Not exactly.

It is better to say:

> `receiptsRoot` is the root hash of the receipt trie containing the receipts associated with the block.

It is **not simply**:

```text
Hash(Receipt1 + Receipt2 + Receipt3)
```

Instead, Ethereum organizes the receipts into a trie structure and derives the root from that structure.

Conceptually:

```text
Receipt 0
Receipt 1
Receipt 2
Receipt 3
      │
      ▼
Receipt Trie
      │
      ▼
Trie Root
      │
      ▼
receiptsRoot
```

This structure makes proofs and authenticated lookups possible.

---

# 21. What Does the Transaction Index Have to Do With It?

Receipts are associated with transactions in a specific order inside the block.

For example:

```text
Transaction 0 → Receipt 0
Transaction 1 → Receipt 1
Transaction 2 → Receipt 2
Transaction 3 → Receipt 3
```

The receipt trie uses the transaction's position/index as part of the trie key.

Therefore, the receipt is associated with its transaction position within the block.

Conceptually:

```text
Index 0 → Receipt 0
Index 1 → Receipt 1
Index 2 → Receipt 2
Index 3 → Receipt 3
```

This allows the receipt trie to organize and authenticate individual receipts.

# 22. What Happens During Block Production?

A simplified version of block processing looks like this:

```text
Transactions
      │
      ▼
Validator / Execution Client
      │
      ▼
Execute Transactions
      │
      ├───────────────┐
      ▼               ▼
Update State       Generate Receipts
      │               │
      ▼               ▼
State Trie        Receipt Trie
      │               │
      ▼               ▼
stateRoot        receiptsRoot
      │               │
      └───────┬───────┘
              ▼
        Block Header
```

The resulting roots become part of the block header.

The block header therefore commits to both:

* the resulting state
* the transaction receipts

# 23. `receiptsRoot` Is Not the Same as `logsBloom`

Another common confusion is between `receiptsRoot` and `logsBloom`.

They serve different purposes.

### `receiptsRoot`

A cryptographic root hash committing to the receipt trie.

### `logsBloom`

A bloom filter designed to help efficiently search/filter for logs.

Conceptually:

```text
Receipt
 ├── Status
 ├── Gas Used
 ├── Logs
 └── Logs Bloom
```

The logs contribute to the receipt data, while the block header also contains a `logsBloom` field.

So:

```text
receiptsRoot ≠ logsBloom
```

The first is a cryptographic commitment.

The second is a probabilistic filtering structure.

# 25. The Complete Relationship

Putting everything together:

```text
                    Ethereum Block
                          │
                    ┌─────┴─────┐
                    │   Header  │
                    └─────┬─────┘
                          │
        ┌─────────────────┼──────────────────┐
        │                 │                  │
        ▼                 ▼                  ▼
transactionsRoot    receiptsRoot        stateRoot
        │                 │                  │
        ▼                 ▼                  ▼
Transaction Trie     Receipt Trie         State Trie
        │                 │                  │
        ▼                 ▼                  ▼
Transactions          Receipts          Global State
                          ▲                  ▲
                          │                  │
                          └──── Execution ───┘
```

This diagram captures the fundamental architecture.

The transactions are executed.

Execution produces receipts and changes the global state.

The transactions, receipts, and state are represented by separate authenticated data structures.

Their roots are committed to through the block header.

# 27. The Most Important Difference

The easiest way to avoid confusion is to remember this:

```text
transactionsRoot
        ↓
Commits to transactions

receiptsRoot
        ↓
Commits to transaction receipts

stateRoot
        ↓
Commits to resulting global state
```

They are three different commitments.

Even though they are all represented as root hashes, they answer different questions about the block.

---

# Conclusion

The `receiptsRoot` is an important field in the Ethereum block header that represents the **root hash of the receipt trie for that block**.

After Ethereum executes the transactions in a block, it generates transaction receipts containing execution-related information such as status, gas usage, and logs.

These receipts are organized into a receipt trie. The root of that trie is calculated and stored in the block header as:

```text
receiptsRoot
```

This gives the block a cryptographic commitment to the receipts produced by its transactions.

The three major roots can therefore be understood as:

```text
transactionsRoot
        ↓
Transactions included in the block


receiptsRoot
        ↓
Receipts produced by executing those transactions


stateRoot
        ↓
Global Ethereum state after execution
```

Together, these roots allow Ethereum's block header to commit to different but closely related aspects of block execution.

The key idea is:

> **`receiptsRoot` is the cryptographic commitment to the transaction receipts generated by executing the transactions in an Ethereum block.**

Once you understand this relationship, the Ethereum block header becomes much easier to understand: **`transactionsRoot` tells us what was executed, `receiptsRoot` commits to the execution receipts, and `stateRoot` commits to the resulting global state.**
